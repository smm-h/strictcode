# `unreachable-code`

:-: rule-facts id="unreachable-code"

## Semantics

A statement is unreachable when it follows, in the same block, a node that always terminates:

- `return`, `raise`, `break`, or `continue`;
- a block whose last statement always terminates;
- an `if`/`elif`/`else` chain with an `else` present where every branch always terminates.

Comments are never statements (lesson 24): a trailing comment after `return` is never reported,
and never hides a real unreachable statement after it. Nested scopes are independent (lesson 25):
a terminator inside a nested function or class never makes the enclosing block's following code
unreachable, and the analysis still descends into nested scopes to find unreachable code there.

The rule runs on every project, test code included. It is not applicable to Go, where `go vet`
already reports unreachable code, and is planned for TypeScript/JavaScript.

## Fix

The tier-1 transform removes the unreachable statements, then re-extracts the graph and verifies
the result; see [fixes](../../fixes/).

## Lineage

The donor ran this check only on libraries, inside the `library-lint` aggregate. It is now a
standalone rule for every project: unreachable statements are a correctness defect anywhere, and
the library-only restriction protected the library-boundary rules, not this one.

## Suppressing

A suppression names a file relative to the workspace root:

```toml
[[rules.unreachable-code.suppressions]]
path = "tools/generated/parser.py"
reason = "Generated by the grammar tool, which emits unreachable fall-through returns."
```
